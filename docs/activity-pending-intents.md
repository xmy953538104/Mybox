# Activity PendingIntent and notification interaction gap

After restoring actual network connectivity on Y700, Play40.0.13 reached `ForegroundCoordinatorService` and crashed while building its foreground notification: `PendingIntent.getActivity → getIntentSenderWithFeature → ServerPendingIntents.create` rejected type 2. This is a missing production capability, not an acceptable test-only failure. The next notification normalization layer also rejects content/delete/full-screen intents and actions, so merely accepting type 2 would not complete the fix.

Focused REA of the original `PendingActivityProxyStub.c` (`ev_dbb839755495db3657f4da9dcf0ff76f1b6bfac5596ed9bae3eba6ebcf38a8cb`, JADX headless 0.7.1, supplied new APK SHA-256 `6fcbaafbcb033b9e0cc03a5d6acaa54ca6b6cb06d16ce3c2d0657d7addfba257`) confirms a physical Activity trampoline. It restores the virtual Intent and user, resolves the target, and dispatches virtual startActivity, preserving a source token/result path where applicable or adding NEW_TASK for a root launch. onCreate finishes the trampoline and moves dispatch onto an executor. This observed dispatch method does not establish the creation, persistence or all flag semantics of the original implementation.

Mylite should extend the existing authenticated capability store and Activity/task routing, retaining a real OS Activity PendingIntent for notification interaction. Creation must not start guest Application or Activity. Sending must revalidate the creator installation and current target, reject tampered/stale/cross-package capabilities, and preserve immutable/mutable fill-in, one-shot, cancellation, update and request-code identity. A signed physical trampoline must survive engine-process death and forward through the existing Activity authorization path. Using a broadcast notification trampoline would change Android's notification-launch policy and is not an equivalent implementation.

Notification content/delete/action capabilities require separate translation and real user-click checks. Tests must observe actual target onCreate/onNewIntent, result/task behavior, actual OS notification dispatch, cancellation and process-death recovery. Returning an invented Binder, dropping the notification, swallowing the exception or pre-launching the target does not satisfy this requirement. The original checkpoint above recorded the missing capability; the candidate implementation below is not yet a usable Play release.

## Candidate reconstruction, 2026-10-25

The focused analysis was repeated with REA `inspect_android_method` against the same supplied APK and provider: `ev_794f308314271e823d1c4df9ec6690f35df534f48187e77a1f03066d58db0883`. It again shows target resolution followed by root NEW_TASK or source-token/result dispatch. Private evidence is retained outside the repository at `analysis/mylite-reconstruction/core-parity/rea-pending-activity-dispatch-20261025.json`; this is static evidence, not proof of original runtime parity.

`ServerPendingIntents` now creates a real OS Activity sender for a single explicit same-package target. Creation reads installed metadata and journals the capability without acquiring a guest process or calling its Application/Activity. The non-exported physical `OsPendingActivity` finishes immediately and authenticates/dispatches on a bounded worker queue, matching the physical entry/async dispatch structure observed in the original. No original source or binary is shipped.

`OsPendingStore` file schema 3 retains version-1/2 file reads and version-1/2 snapshot reads, preserving existing broadcast key identities. The authenticated snapshot includes sender type, creator package, installation path/generation, virtual UID, exact signer list, intent, key identity and revision. Activity targets are confined to that same installation, so the creator pin also pins the target generation/signers. The server checks enablement when creating and sending, and the Activity/task preparation compares the process actually acquired against that expected generation. A new generation cannot silently receive an old capability. Guest startup is outside the PendingIntent mutation queue, because guest Application.onCreate may itself create a PendingIntent.

Activity creation materializes a real OS Activity PendingIntent immediately, while guest APIs return the existing working Mylite Token Binder, consistently with broadcast/Service capabilities. Guest info/send/cancel hooks resolve that retained virtual capability; sends dispatch through its actual OS PendingIntent. At a real system boundary, `forNotification(caller, supplied)` authenticates the held virtual capability and supplies the real OS sender. The virtual Token is never passed to Android's notification manager as an invented OS record.

Keeping the client-held Token solves cancellation lifetime without a tombstone table: even after removal from the active-key map, Binder references retain the canceled Token so old PendingIntent/IntentSender sends report cancellation and creator/type metadata remains available. Client parcel transfer preserves the same capability. Real notifications and cold-server tests independently inspect/send the physical OS record. No privileged AMS `getIntentForIntentSender` readback is used to recover a canceled OS sender's owner.

`forNotification(caller, supplied)` requires the authenticated posting identity to remain installed and verifies the registered creator, generation and live OS record; host UID or package equality alone is insufficient. It permits another authenticated app to post a held capability, matching Android's transferable PendingIntent semantics; delivery retains the original creator's pinned authority. Broadcast/Service notification actions still require their own physical-delivery implementation.

Guest sends encode mutable fill-in separately from the signed base, apply Android Intent.fillIn with the virtual flags and validate the result before consuming an OS one-shot. The physical sender never grants replacement of its trampoline component/action/data. Immutable senders discard fill-in; UPDATE_CURRENT replaces signed extras without changing the OS sender; CANCEL_CURRENT/cancel and NO_CREATE consult the same physical identity. Direct OS notification dispatch currently transports mutable extras; arbitrary component/action/data replacement from an external OS sender, multi-Activity stacks, ActivityResult/source-token linkage, options, URI grants and non-supported Parcelable extras remain explicit gaps, not reduced project scope.

The first emulator run exposed two incorrect assumptions, which remain recorded as failures: base extras win over duplicate fill-in extras in AOSP14 Intent.fillIn, and ordinary PendingIntent.send(context, ...) automatically adds the context's callerDisplayId option. Assertions now require an existing base key to survive, a new mutable key to arrive, and a new immutable key to be ignored. Send accepts only the integer `android.activity.callerDisplayId` for the actual current host default Display, uses that actual Display's context and passes the checked Bundle to the physical seven-argument send. Whitelist tokens, required permissions and other options remain rejected. A valid non-default display is explicitly rejected because final guest task propagation through ServerActivities is not implemented; it is never accepted and silently redirected to the default display. A pure policy test compares against a nonzero actual-default ID to reject an assumed zero or a different valid display, and the runtime fixture rejects real secondary displays when available. The official AOSP14 Intent, PendingIntent, ActivityOptions and ComponentOptions sources are retained privately under core-parity.

Core CI 40204835042 subsequently rejected an ordinary send because the first options patch incorrectly assumed that the caller-display key was the only serialized framework option. Full review of the field initializers, both constructors, complete toBundle and ComponentOptions confirms that AOSP14's basic splash-screen style starts at UNDEFINED while toBundle writes it whenever it is not zero. A basic options Bundle can therefore contain an additional default entry; Bundle reconstruction also has different omitted-key defaults. The fix derives the default baseline from this running framework's `ActivityOptions.makeBasic().toBundle()`, accepts each supplied default entry only with exactly the same Java type and value, permits the separately validated caller-display entry, and passes a complete defensive copy onward. It does not add omitted keys, discard baseline entries, accept unknown keys, or authorize custom/privileged values. Runtime boundary tests use the actual framework baseline, require its complete preservation alongside display, and reject changed values/types for every baseline key. The failed CI remains a failure; this patch awaits execution.

The OS captures a signed delivery snapshot before a later cancel/update can change its live record. Activity admission therefore checks the captured snapshot's HMAC, boot, installation and target, without requiring that its capId/revision still occupy the current active key. Active-key lookup, cancellation and replacement are separate from delivery authorization: NO_CREATE or OS cancellation cleanup cannot erase a previously accepted delivery, and UPDATE_CURRENT cannot rewrite its old extras.

One-shot admission has its own durable capId ledger, atomically committed before starting guest code. It accepts each capId once even after key replacement or server death. File schema 3 stores this ledger independently of active records, scoped to the current boot and bounded to 65,536 IDs plus the existing file-size limit. Copy-on-write means an I/O rejection does not publish an in-memory claim; errors propagate to the physical-entry failure log. A crash after the durable claim but before guest launch remains an at-most-once lost/uncertain delivery; no cross-system exactly-once transaction is claimed and the engine must not silently replay it.

Cancellation of future sends is enforced by the actual OS PendingIntent. The non-exported entry accepts a previously signed delivery envelope even if the live OS capability has since been canceled, as needed for accepted in-flight sends. Like the existing Alarm model, this does not prove isolation against code that already bypasses the shared-UID container boundary and steals/replays a raw signed envelope; no kernel-level ability to attest the original OS acceptance time is claimed. Real OS interleaving tests remain required.
