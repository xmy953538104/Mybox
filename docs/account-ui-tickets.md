# Mylite cross-package account UI

2026-10-27 account-discovery candidate: original typed authenticator query `a.y` (`ev_43400bb5aaabc81713978718192f7aec649e908d69b35facd10837157caf5d72`) enables managed-hidden projection; the common filter (`ev_b61d1365ac0e2bed4b81f9af75a040530db275155aefe44f0921a2b0b186296f`) accepts visibility 1/2 and, for that query, 4. Public visibility (`ev_886177ef394ada8476c8ade5abde828ec2e47a33dbc644e02f6c5c92b7707d70`) supplies legacy defaults 2/4; permission, target SDK, owner UID/signature and stored-visibility helpers were checked together. This matches [AOSP14 typed-owner projection and filtering](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-14.0.0_r1/services/core/java/com/android/server/accounts/AccountManagerService.java). The pinned [microG AccountContentProvider](https://github.com/microg/GmsCore/blob/32bc8954ff872d0e1a05ddfae81561b6dbecef69/play-services-core/src/main/java/org/microg/gms/auth/AccountContentProvider.java) actually uses this typed-owner API to discover accounts for its checked caller.

Mylite previously aliased it to ordinary enumeration and gave unset target visibility the hard-hidden value 3. The candidate separates named-owner projection, default managed-hidden value 4 and explicit hidden value 3. Projection is read-only and grants no enumeration/token/password access to the target. Ordinary consumers and retired owners remain denied; real installed target signers are consulted. Null-type cross-package projection retains the existing owner restriction and excludes managed-hidden entries. The framework fixture uses another actually installed consumer APK without starting another VM, checks live hide/reset queries on the same AccountManager, and retains ordinary-consumer negative tests. JVM fixtures separately reject another package with the same signer and replaced owner/consumer signers. Y700 has a retained account row but Play still asks to sign in; this is a verified API defect and a candidate cause, not proof that its server credential remains valid. No user account data or privacy switch is rewritten.

The account server freezes the consumer and authenticator's real signers and committed APK generations before asynchronous authentication. An authenticated response may authorize one exact standard Activity owned by that authenticator. A bounded, expiring Binder ticket carries that authority; unrelated packages, compatible signature views and the shared physical UID cannot grant it.

The server retains the original Intent, extras and response Binder. Launch restores that snapshot, rejects structural changes and consumes authority at the real Activity token claim. Both installed principals are checked again at reservation, dispatch and claim. A definite failure may release an unclaimed ticket only after its old record is retired; uncertain dispatch, expiry, changed installation or a completed claim cannot be retried. With expectActivity=false, the returned Intent has its own bounded lifetime after the original Future closes.

Two independent fixture APKs exercise automatic UI/result delivery, a delayed manual launch, the original response/payload, same-signer wrong-package rejection, replay, actual AMS failure and signed updates. Internal consumption-boundary tests separately check updates after reservation. The suite runs in its own process-slot group three times, retaining data between rounds. Five JVM state tests and local APK/lint checks pass. At `83181b3`, all three independent B2a rounds passed in both [core CI40073849217](https://github.com/xmy953538104/Mybox/actions/runs/40073849217) and [bundled CI40073850240](https://github.com/xmy953538104/Mybox/actions/runs/40073850240). The workflows still failed: core had a native initialization EBUSY before an ordinary authenticator bind; bundled registration lacked a real host network permission. These separate failures remain acceptance blockers.

B2b adds explicit authenticator-owned singleTask UI through the existing task queue. Each launch binds its ticket to an exact Activity record and operation Binder/id. Both installed principals and live processes are checked before clearing children and again before payload delivery. Creation consumes authority at the real token claim; reuse consumes it when the framework new Intent is unwrapped. A lifecycle ACK cannot complete an operation whose payload was never claimed. Queued failure, partial clearing, timeout, process loss or uncertain dispatch burns the grant; the standard B2a definite-start rollback remains separate.

The independent fixture keeps an authenticator UI alive and handles each new response explicitly in `onNewIntent`. It checks distinct real account Futures, same instance/token/task, unchanged `getIntent()`, same-token configuration recreation followed by another real response, actual destruction of children in two processes, another physical task remaining intact, immutable payload and response, premature or forged ACKs, replay, and rejection after a partially completed clear. The original standard UI/result/update checks remain. Seven JVM ticket tests pass. At `3112332`, the expanded suite passed all three independent Android rounds (8.982/4.225/4.646 seconds) in [core CI40077565789](https://github.com/xmy953538104/Mybox/actions/runs/40077565789); the ordinary 38-test suite also passed three rounds. The partial-clear failure is a controlled protocol rejection after a real child destruction, not a reproduction of an actual OS timeout. These fixture results do not establish real Google login.

The pinned microG LoginActivity reads its response only in `onCreate`. Cross-package requests for it are rejected while a ticket is outstanding or its exact UI record still exists, including after account-session completion. A generic fixture's successful reuse would not demonstrate overlapping microG login support. Its manifest and private response state are not modified.

An authenticator's final `addAccount` result is separate from account visibility. The server still authenticates its real owner, validates the returned account type and current consumer signer, and strips any unsolicited token; it does not require or create an enumeration/token grant for that result. Other account operations retain their existing visibility and token checks. This follows [AOSP14 addAccount/Session](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-14.0.0_r1/services/core/java/com/android/server/accounts/AccountManagerService.java). The independent hidden-account fixture requires a real successful Future followed by denied enumeration, password, user-data, raw-token and token requests. Local 53-test JVM/build/lint/audit checks pass. At `7947e40`, all three extended account UI rounds passed in [CI40078946863](https://github.com/xmy953538104/Mybox/actions/runs/40078946863); that workflow still failed an unrelated component fixture's start/bind ordering assertion in its first ordinary round, retained in STATUS.

Task-mode `startActivityForResult`, other cross-package launch modes, foreign-package clear victims, arbitrary exported-app navigation, account chooser/system UI, URI grants and server-death ticket recovery remain unsupported. This is not acceptance of real Google login, Play or push.
