# Observed Play startup boundaries

The private diagnostic uses the original bundled Play40.0.13 APK (SHA256 `c56dedb39391b25ab35b25d8045300f0147582026a74d2d8f1e581b2cebcb88a`, actual Google signer `f0fd6c5b410f25cb25c3b53346c8972fae30f8ee7411df910480ad6b2d60db83`). It is not a repository asset or a public CI input. No real Google account is present in this disposable emulator. Every failed round remains separate.

- Round8 failed at actual JobScheduler.enqueue of a virtual PhenotypeUpdateService. The new [OS job bridge](jobs.md) let round9 pass this point; round9 then failed loading `org.apache.http.ProtocolVersion`.
- Builtin system libraries are selected from the real Android registry using base/split uses-library declarations, with required/optional semantics. LoadedApk receives the actual SharedLibraryInfo objects and paths. It does not use original GBox libraries or inject an unrelated APK. Original library-file helper REA `ev_7156c163cd7bde98eb59ab61191fbe22f9220ecca1c8b1fd2bf75bbf54a02900`. Dynamic APK/static SDK libraries and complete PM library metadata parity are not accepted.
- Round10 reached MainActivity but physical privileged user enumeration failed. The container's existing single virtual user now has its own user/profile discovery view; no physical user-management privilege is granted. The original user-manager registration constructs UserInfo0 and a singleton user list (`ev_85e3a66dfe63b7339959e8b3a29a72a6d9b0b33a157014dfebc8172b94eabf48`; registration strings remain obfuscated). A new constructor initially rejected SYSTEM flags in round13; Android30+ now uses the explicit typed constructor. Virtual owner-name discovery reports no owner registered in the container, while other physical policy enforcement remains Android's. Original device-policy registration evidence is `ev_ccdcf23009aab276576a7043dfdd067411b15d52ce02e1a1e2552cc8b90c0e90`; this is not evidence of full management API parity.
- Rounds11/12 and18 entered the Store's own recovery mode after accumulated startup crashes. The requested singleInstance RecoveryModeActivity and flags `0x34c00000` remain unsupported, as does the subsequent recovery foreground-service sequence. REA of the actual Store redirect `ev_e8cefc4515a3324f250ca09dbcd838b45999eecaaaa04cb34aaa8aa97f8946e5` confirms this is its recovery branch. The disposable Store CE/DE data through round12 were preserved by renaming them to private-inputs/play-state-round12-ce/de before testing a fresh Store profile; no microG/account data was cleared. Fresh-profile diagnostics must be reported separately from recovery-mode acceptance.
- Rounds14/15 then reached main Activity lifecycle but privileged profile/device-owner name reads failed; both observed read-only user-zero paths now use the virtual no-owner model. Round16 obtained RESUMED then died in background at getInstallerPackageName; the process-survival assertion correctly rejected it.
- Installer provenance now publishes atomically with verified APK records. Manual imports/legacy records have no virtual installer. Session commits pass the authenticated installer, recheck its actual installed appId/certificates under the package publication lock, and record its package. Interrupted-commit recovery requires both exact APK bytes and the recorded installer. Installer-package reads for virtual targets use these records, never physical Google identities. Original getter REA `ev_379f7a22d87dbd5c135dd848f1c39716dba068f199618948ea369b1b54ae30e3` required smali fallback. Full InstallSourceInfo APIs are not yet implemented.
- Round17 obtained RESUMED but died in storage initialization: FileStorageUnavailableException reported Direct Boot despite the actual OS user being RUNNING_UNLOCKED. REA `ev_6acd92699dbc2ff467d72d1237302f88a7177036f54fec961150af0200545fec`, `ev_77758c408192ff16c7d8f212ba4ead89631b7aee6ff61235854780cfa092c536`, and especially `ev_64b40ce2e37b19e6551eefcf11813b2a5daf355013f1726046442a2f7c91d6d5` show its helper queries a disabled DirectBootHelperService with flags `0x10000200`. Our explicit/implicit resolution incorrectly discarded disabled components even with MATCH_DISABLED_COMPONENTS. Resolution now respects that flag and applies actual user-unlock/direct-boot filters. It does not force isUserUnlocked true. A signed disabled-service fixture and locked/unlocked filter negatives cover this boundary; real Store startup after this change still needs acceptance.

Separate cloud issue: core40103787982 failed in its first component-state restart phase because an already-cached raw Settings Provider bypassed the physical attribution wrapper and rejected the guest package under the real host UID. Later rounds and total bundle40103789885 succeeded, which does not erase that failure. Binding now adapts preexisting Settings System/Secure/Global provider caches through the same identity-checked wrapper, preserving the actual remote Binder and attribution token. A new test explicitly installs a pre-binding cache, verifies adaptation once and restores all touched caches. Android8.1/12/14 Settings source layouts were retained separately. CI now rejects unexpected owned-UID Java/native crashes even if instrumentation reports success, and rejects inability to collect that evidence.

Actual account authentication, Play catalogue/download/install, recovery-mode compatibility, Maps/FCM and OEM/performance parity remain unaccepted.
