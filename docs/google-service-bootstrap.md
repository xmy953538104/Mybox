# Google service bootstrap and recovery

The reference preset microG (SHA2569025b3c5dadb589118abe6984badf2e0952384a41f1ae5d6b31851e0d44954b0) defaults checkin/GCM ON and respects explicit preference overrides. The exact REA configuration/setter evidence and derived-carrier limits are in [reference configuration](microg-reference-configuration.md). Pinned upstream32bc8954ff872d0e1a05ddfae81561b6dbecef69 defaults both OFF. Patch0013 adds the existing checkin_enable_service/gcm_enable_mcs_service manifest metadata, without modifying settings precedence or stored credentials. Turning a default on alone does not implement recovery.

Original TriggerReceiver REA Java (`ev_f8dcd7a9ea47d1c8fbdee896fbde00578dd737ebc723632c5630d1f8931782d4`) displayed an apparent contradictory offline branch. The focused original-Dalvik disassembly (`ev_86137a8967dbab4c143e83124701f9e8c2e08bb6cfd7c730f09cca4f5fb026e5`) contains181 instructions whose bytes were checked against the unchanged original DEX. At0x10018e864, a true enabled-network result branches to the MCS connection/start path at0x10018e8d0; it does not enter the offline block. Java pseudo-code and the disassembler's ESIL expression were not copied as semantics. The [official Dalvik conditional instruction definition](https://source.android.com/docs/core/runtime/dalvik-bytecode) and actual opcode operands resolve that discrepancy. This is static control-flow evidence, not original-runtime acceptance.

Original process-death/Google wake chain is process manager am.u.t0 → AppProcessKiller.N → manager.x.o (`ev_f795d05f8dc968f25e138641a0c08869486c3fec675fd8a1a60b99801a87cbd3`, `ev_cf60db77464218f841840b0fe2509123d4626b5dc167d262ac81e14d5bd158f5`, `ev_98a78f901c4034b6f460abc726455bc645519bf8150d2b4f85eca07b376a3fc2`). It checks device environment/install state and GMS main/persistent processes, then starts its account/MCS services. Original physical StubService checks an initialized process/user before dispatch (`ev_afb86e73af5c651854df07760b165ee02c4fd1b6988eba63b341b9517a3e2ed5`); invalid cold starts return NOT_STICKY. These methods do not establish general ServiceConnection replay, native process bootstrap or HMS requirements.

Mylite uses its existing pinned-package and current-generation checks, then the normal explicit TriggerReceiver RECONNECT. It never sets FORCE_TRY_RECONNECT for automatic/host recovery, never impersonates a system caller, and never overwrites user OFF. Pinned upstream CheckinService schedules a normal reconnect after successful registration. Real OS broadcast and Service alarm paths remain separate. After a persistent VM death, recovery waits for its exact old ProviderConnection to close successfully before requesting a new guest; confirmed Binder death alone is insufficient. Automatic attempts persist across server restarts and are bounded to three per boot/generation/five-minute window. A manual prepare records the user's request and resets that budget. Errors/exhaustion remain visible in the Home status. This is a bounded independent design, not a claim that the original uses the same retry policy.

Physical GuestServiceStub captures its actual authorized GuestComponents owner. An unbound cold OS restart stops without guest execution. A start with no current lease or already-consumed payload cannot invoke guest callbacks; an already running authorized Service is preserved. This does not implement arbitrary sticky/redelivery or foreground-Service OS capabilities.

Candidate cloud coverage includes default ON and explicit OFF surviving page recreation, real anonymous registration, actual MCS successful server LoginResponse, a real OS Service heartbeat with an outbound ping followed by inbound ACK on the same live process, Play registration-token existence without reading its value, actual emulator network loss/recovery, persistent-VM death followed only by passive OS observation, and explicit OFF/ON. Airplane-mode control is confined to the disposable emulator and follows [AOSP CTS usage](https://android.googlesource.com/platform/packages/modules/Connectivity/+/cce6a8bc0a83a74279b8b1e4f90200e819aa19e0/tests/cts/net/src/android/net/cts/ConnectivityManagerTest.java); it must actually disconnect, and restoration is requested in finally. UI `Connected` alone is insufficient. No Firebase project exists, so end-to-end foreground/background/screen-off delivery remains unverified. Account authentication, Play download/install, ARM/OEM behavior and measured reference performance remain required unfinished work.
