# OS JobScheduler reconstruction

Actual Play subsequently exposed public expedited jobs (`flags=0x10` on API31), which the conservative flag gate rejected. Mylite now preserves that bit through the signed original and physical JobInfo and lets Android apply the real host UID's quota/result. Other privileged/unknown flags remain rejected. A real expedited fixture observed `JobParameters.isExpeditedJob()`, original ID and genuine completion/removal (first local pass 1.196 seconds). Because all guests share the host UID, this does not provide per-guest OS expedited quotas.

A later manual Play reopen crashed on a valid executor's terminal callback arriving after its Mylite session closed. Caller PID/generation/Binder and job-ID checks remain mandatory, but a legitimate callback now still reaches the original Android callback, which decides whether that execution is current. The fixture calls jobFinished twice and only publishes after both framework callback messages return. All six Job tests plus private Play startup passed in 100.967 seconds. The original copies JobInfo, saves virtual job/user/component fields in extras, substitutes a physical ProxyJobService and maps job IDs. Its service connection obtains the actual guest IJobService and forwards start/stop. Callback methods translate the physical job ID, including dequeue/completeWork. Its failure helpers can report completion without a real guest result; Mylite must preserve visible failure instead of treating those helpers as acceptance. Original hash-derived job IDs can collide, so allocation must check actual OS jobs.

Implementation boundary: registered guest PID/package/generation -> server -> actual OS scheduler -> permission-protected physical service -> current guest JobService -> authenticated real callback. OS constraints, work IDs and rescheduling remain authoritative. Use the platform Binder transaction constants, since Android 14 inserts callback methods and changes scheduler namespace signatures. No shadow framework AIDL definitions or fake task acknowledgements.

Nonpersistent jobs can carry a bounded signed original JobInfo in physical extras, leaving Android as the source of pending-job truth. A dedicated job-proxy process can expose genuine Binder death to Android if the guest executor or server dies. This avoids silently leaving a live physical service after its executor has vanished. Ordinary host/engine processes must not be killed as a workaround.

Initial unsupported shapes must reject explicitly: reboot-persisted jobs, URI grants/content triggers, nonempty transient extras, privileged scheduling/notifications and unknown protocol versions. These are implementation limits to extend when actual Google callers require them, not claims of original parity.

Required verification: real constrained scheduling, owner/namespace isolation, two actual OS work items and completion results, stop/reschedule/cancellation, cold engine startup, executor/server deaths and forged callers. Then repeat actual private Play startup and continue login/download/install. Fixture success does not satisfy this business goal.

The first implementation uses actual OS records, authenticated bounded envelopes signed with a domain-separated HMAC under the existing OS capability key, collision-checked physical IDs, and current installed creator certificates/appId. It validates the enabled BIND_JOB_SERVICE declaration at submission and execution. Android retains constraints and work IDs; callback forwarding checks the actual executing reservation and restores the original virtual ID/extras/namespace. Unsupported privileged callbacks remain explicit errors. The physical proxy uses its own `:engine_jobs` process, protected by BIND_JOB_SERVICE and system-UID checks. Its owner/server death guards retire only that proxy, allowing Android to observe genuine IJobService death and retry. Callback cleanup unbinds asynchronously to avoid deadlocking a synchronous guest main-thread callback.

Both recoveries preserve the same original fixture nonce/job ID, use new guest/proxy PIDs, and the latter cold-starts a new server through the original OS job; the host does not submit or force-run a replacement. Android's observed rescheduling takes roughly 40–46 seconds despite a 10-second requested backoff. These are emulator results, not OEM timing guarantees.
