# Mylite foreground Services: first checkpoint

Each started guest Service leases its own real Android Service stub and token; four slots are available per guest process. `startForegroundService` retains the actual foreground requirement. Android's onStartCommand drives the guest callback; promotion/stop use the corresponding real OS token. Start IDs, independent stopSelf, pending starts, REMOVE and DETACH are tracked separately for each Service. A fifth simultaneous started Service fails explicitly.

Notifications/channels/groups are mapped into a server-controlled namespace based on virtual user, package and real certificate. Original tag/ID pairs, including negative IDs, map to persistent distinct physical IDs. Supported platform templates are rebuilt with host-usable icons and resources. Foreground success depends on Android accepting the real promotion; an internal boolean is not acceptance. Requested foreground types remain constrained by actual host capability and verified package/service identity.

The fixture checks two simultaneous independent foreground ServiceRecords and real posted notifications/channels, icon/progress conversion, repeated starts, stale start IDs, independent stopping, REMOVE/DETACH and slot exhaustion. Runtime tests must observe OS state, not merely a guest report.

Current limits: sticky/redelivery recovery after OS process death; authenticated task-removal callback restoration and STOP_WITH_TASK; custom RemoteViews, interaction PendingIntents, bubbles and unknown styles; additional foreground types/permissions and guest-specific sound URI forwarding. Unsupported guest requests fail explicitly; unverified task-removal payloads are not forwarded across guest boundaries. This is not complete microG registration/MCS or Play download acceptance.

The previous started-only Mylite check therefore rejected an actual bound Play coordinator. The candidate passes the admitted carrier as a local Java reference, never as guest IPC data, before guest onCreate/onBind; foreground changes reach real Android and logical destruction clears the owned notification. Another bound guest cannot remove the owner's foreground state. The pool currently permits one bound-only foreground owner per VM; contention is explicit, not silent notification takeover. Independently started services retain their four separate carriers.

The original Play40 manifest declares SYSTEM_EXEMPTED for `com.google.android.finsky.foregroundcoordinator.impl.ForegroundCoordinatorService`; the candidate verifies the real Store publisher and maps this exact coordinator's manifest-default request to ordinary DATA_SYNC. It does not grant a system exemption. The fixture must independently observe the bound OS ServiceRecord as foreground, its real notification and cleanup without a guest onStartCommand; this remains pending CI and an actual Store retry.
