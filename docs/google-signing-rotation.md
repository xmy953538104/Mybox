# Verified APK signing rotation

One actual official Play image exposed version85361640 with a new current signer and the old Google certificate in Android's reported history. That history is diagnostic input, not authority. Production keeps the original Google SHA256 anchor `f0fd6c5b410f25cb25c3b53346c8972fae30f8ee7411df910480ad6b2d60db83`; no new leaf certificate is allowlisted.

`SigningIdentity` can only be constructed from successful apksig verification. Its effective current certificate follows the running platform's v2/v3/v3.1 selection. A verified proof-of-rotation must terminate at that current certificate. Google publisher roles accept a single current certificate that is either the original anchor or its cryptographically proven successor. Package names, compatibility signatures, record history strings and an unrelated APK signed by the new key cannot create that proof.

Store import checks the copied and verified complete APK set before publication. Launch, installer authority, the narrow account-change broadcast route and setup/download foreground-service translation consume the same sealed-generation evidence. They do not individually add new certificate exceptions. microG's exact APK/certificate pin, registered caller identity and existing capability generation checks remain exact.

Package updates retain the current signer set or require a verified forward lineage with installed-data capability for the previous current signer. Reverse/conflicting lineage, downgrades and inconsistent split signatures are rejected. CE/DE data and appId remain in place. Base and split APKs are verified individually; a current-key split can omit redundant lineage, but a conflicting proof cannot extend the base publisher's authority.

Cold processes reconstruct proof from the immutable APK set rather than persisting trusted history properties. A bounded per-generation cache checks current records, every APK's FD/path identity, regular/read-only state and nanosecond timestamps. Changed files, permissions, generation or clock offset invalidate it. Full verification holds only that generation's monitor, without a package-registry/cache lock; concurrent reads share a stable result. API26 and the Windows JVM fallback remain deliberately uncached. Actual Android cold/hot latency remains to be measured.

Real fixture APK tests cover platform-selected v3.1 rotation, directional data-preserving upgrades, installed-data capability, split consistency, corrupt proof, record-string forgery, cache invalidation and import rejection before publication. These establish the mechanism, not acceptance of the actual new Google sample. Its exact APK proof and Android behavior still require verification. Effective-signer migration after an Android SDK upgrade is deliberately rejected until package records and account ACLs can migrate together; silently rewriting current certificates would break existing authorization semantics.
