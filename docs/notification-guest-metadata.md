# Notification metadata and the server boundary

The retained-account Y700 run of `8107456` reached Play's download metadata response and created an OPEN installation session, but staged no APK. Its download process then crashed in `DownloadService.startForeground`: our notification Binder round trip returned `BadParcelableException` for Play's private `ProtoParsers$InternalDontUse`. This is a captured runtime failure, not evidence of a network failure or a completed installation.

The original GBox foreground hook maps the notification identifier/channel, adapts the notification in its guest process, and passes it to the real proxy Service. Focused REA confirms `q1.I → z7.b → z7.m`, including channel configuration, resources/icons and the public notification. The retained `client.virtualservice.g.i` evidence terminates at the physical Service token. This does not establish complete original notification parity.

Mylite now keeps the notification body and guest-only Parcelable metadata in that guest VM. Its authenticated server maps IDs/channels/groups and resolves every content/delete/full-screen/action PendingIntent against the existing creator, generation and actual OS capability. Only framework names and PendingIntents cross this preparation boundary. The guest then posts through the real notification service or promotes its real Service, with host attribution and the physical Android user. Real OS permission checks, foreground Service types, errors and completion remain in force. Cancellation and active-notification queries still use the server's existing namespace. No account files, installer journal or persisted notification-ID format change.

Regression fixtures put a Parcelable class absent from the host class path into action extras. Both ordinary and foreground notifications must actually appear in Android and return that value through the guest's ordinary active-notification API. The existing System UI content/action touches and revoked, stale, mutable and unsupported Service capability checks remain required. Full cloud batches and the retained-account Play download/install/open journey are still required; this candidate is not yet accepted.

Custom views, additional styles, RemoteInput, bubbles and shortcut/locus behavior retain their existing explicit unsupported status. This fix does not claim those remaining core obligations are complete.
